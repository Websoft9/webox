## 1. 引言

### 1.1 目的
提供统一的服务器资源管理功能，支持服务器的接入、配置、操作和维护，为应用部署提供基础设施支撑。

### 1.2 范围
- **功能边界**：服务器生命周期管理（接入、配置、操作、移除）
- **非目标**：不涉及服务器性能监控、基础组件管理、物理服务器采购、网络基础设施配置

### 1.3 背景
在Websoft9平台中，服务器作为基础设施层的核心资源，需要提供标准化的管理界面和API，支持多种操作系统和云环境。服务器监控功能由专门的监控Feature实现，基础组件管理由独立的Feature处理。

## 2. 功能概述

### 2.1 功能定位
服务器管理模块作为Websoft9平台的基础设施管理层，提供服务器资源的全生命周期管理能力。

### 2.2 核心特性
- **间接通信架构**：服务器管理不直接与Agent打交道，通过任务管理Feature下发任务
- **状态缓存机制**：从Redis缓存读取服务器、Agent、Docker状态，不主动连接Agent
- **SSH功能条件性**：仅在网络可达时提供终端和文件管理
- **文件管理简化**：API仅提供基础CRUD，复杂功能由前端组件实现
- **数据来源分离**：配置数据存储于MySQL，实时状态数据缓存于Redis

### 2.3 目标用户/使用场景
- **系统管理员**：服务器接入、配置管理
- **开发人员**：应用部署前的服务器选择和环境检查
- **运维人员**：服务器状态监控、故障排查、批量运维

### 2.4 功能详情

1. 【服务器查询】

支持分页查询和多条件筛选，查询条件包括：

| 查询条件   | 示例         | 描述                                                   |
| ---------- | ------------ | ------------------------------------------------------ |
| 服务器名称 | web-server-1 | 文本输入框，支持服务器名称关键词的模糊查询。           |
| 服务器状态 | 运行中       | 多选下拉选项，支持按服务器状态筛选，参考附录状态字典。 |
| 资源组     | 生产环境     | 单选下拉选项，支持按资源组筛选。                       |
| 更新时间   | 近7天        | 日期范围选择器，支持按接入时间范围筛选。               |

2. 【服务器列表】

按照服务器名称排序，以列表方式展示已纳管的服务器，展示信息包括：
- 服务器名称、服务器状态、操作系统信息
- 主机地址（IP或域名）、SSH端口、SSH连接状态
- 接入时间、最后心跳时间
- 所属资源组、服务器描述
- 操作按钮：管理、终端、文件管理、重启、更多操作

3. 【服务器新增】

通过服务器配置向导分步添加新服务器：
- 【添加服务器】填写服务器基本信息并保存到数据库
- 【检查环境】验证SSH连接并获取系统信息
- 【安装组件】自动安装Websoft9 Agent等必要组件
- 【完成确认】显示接入结果和服务器基本信息

4. 【服务器配置】

支持修改服务器的配置信息：
- 【基本信息】服务器名称、描述、资源组
- 【连接配置】主机地址、SSH端口、登录凭据
- 【权限设置】终端访问权限、文件管理权限、ROOT登录权限

5. 【服务器操作】

- 【终端访问】提供Web终端界面，支持命令行操作（SSH可用时）
- 【文件管理】提供Web文件管理界面，支持文件上传、下载、编辑（SSH可用时）
- 【系统服务】查看和管理系统服务的启停状态
- 【系统信息】查看硬件信息、系统版本、内核信息

6. 【服务器移除】

通过服务器移除向导安全移除服务器：
- 【移除前检查】检查是否有运行中的应用和任务
- 【应用迁移】提示迁移或停止服务器上的应用
- 【Agent卸载】卸载Websoft9 Agent客户端
- 【完成确认】确认移除操作并清理相关数据

7. 【服务器详情】

点击服务器名称进入详情页面，包含：
- 【基本信息】服务器配置、系统信息、网络信息（来源：MySQL + Redis）
- 【应用列表】运行在该服务器上的应用实例
- 【系统服务】系统服务的状态和管理
- 【操作记录】服务器操作的历史记录

8. 【批量操作】

支持多选服务器进行批量操作：
- 批量重启/关机
- 批量修改资源组
- 批量更新Agent
- 批量执行命令
- 批量配置同步

## 3. 依赖关系

### 3.1 依赖Feature列表
- **用户管理**（强依赖）：服务器权限控制和所有者管理
- **项目管理**（强依赖）：服务器资源组织和项目资源分配
- **权限管理**（强依赖）：服务器操作权限控制
- **密钥管理**（强依赖）：SSH认证凭据的安全存储和管理
- **任务管理**（强依赖）：服务器任务的调度平台，Agent 从它获取任务并返回执行结果
- **审计日志**（弱依赖）：服务器操作审计记录

### 3.2 依赖服务与接口契约
- **认证服务**：JWT Token验证，API调用权限检查
- **权限服务**：RBAC权限验证，操作授权检查
- **密钥管理服务**：SSH凭据存储、检索和管理，支持密码和私钥两种认证方式
- **审计服务**：操作日志记录，审计事件上报

### 3.3 基础设施依赖
- **MySQL**：服务器配置数据存储（配置、状态、关系数据）
- **Redis**：实时状态数据、会话存储、任务队列（Agent写入的动态数据）
- **gRPC**：与Agent的安全通信（支持双向流）
- **WebSocket**：Web终端实时交互

## 4. 业务目标与用户故事

### 4.1 业务目标
1. **提高运维效率**：通过统一界面管理所有服务器，减少手动操作
2. **简化接入流程**：提供向导式服务器接入，降低使用门槛
3. **保障基础环境**：统一管理基础组件，确保环境一致性

### 4.2 用户故事

| 运维人员 | 作为运维人员，我希望能够批量管理多台服务器，以便提高运维效率 | ✓ 支持多选服务器<br>✓ 批量执行操作<br>✓ 显示操作进度和结果 |

## 6. API 与契约

### 6.1 总则
- **统一前缀**：`/api/v1/servers`
- **认证方式**：JWT Bearer Token
- **响应格式**：`{code: int, message: string, data: object}`
- **分页规则**：`page`、`page_size`参数，返回`pagination`信息

### 6.2 API接口汇总

**接口总数**：15个核心API接口


| 序号 | 接口名称 | 方法 | 路径 | 功能描述 | 实现方式 | 依赖模块 |
|------|----------|------|------|----------|----------|----------|
| 1 | 获取服务器列表 | GET | `/api/v1/servers` | 分页查询服务器列表，支持筛选 | - | 用户管理、项目管理 |
| 2 | 添加服务器 | POST | `/api/v1/servers` | 添加服务器基本信息到数据库 | - | 用户管理、项目管理、密钥管理 |
| 3 | 获取服务器详情 | GET | `/api/v1/servers/{id}` | 获取指定服务器的详细信息 | - | 用户管理、项目管理、应用管理 |
| 4 | 更新服务器信息 | PUT | `/api/v1/servers/{id}` | 修改服务器配置信息 | - | 用户管理、项目管理、密钥管理 |
| 5 | 删除服务器 | DELETE | `/api/v1/servers/{id}` | 从平台移除服务器 | - | 应用管理、审计日志 |
| 6 | 检查服务器状态 | POST | `/api/v1/servers/status` | 检查单个或多个服务器的SSH、Agent、Docker状态 | SSH直连+MQ通信 | 密钥管理、任务管理 |
| 7 | 服务器操作 | POST | `/api/v1/servers/actions` | 执行单个或批量服务器操作 | MQ通信 | 任务管理 |
| 8 | 获取批量操作状态 | GET | `/api/v1/servers/actions/{batch_id}/status` | 查询批量操作执行状态和结果 | - | 无 |
| 9 | 获取终端访问 | GET | `/api/v1/servers/{id}/terminal` | 获取Web终端访问URL | SSH直连 | 密钥管理 |
| 10 | 列出目录文件 | GET | `/api/v1/servers/{id}/files` | 列出服务器目录文件 | SSH直连 | 密钥管理 |
| 11 | 上传文件 | POST | `/api/v1/servers/{id}/files` | 上传文件到服务器 | SSH直连 | 密钥管理 |
| 12 | 下载文件 | GET | `/api/v1/servers/{id}/files/download` | 从服务器下载文件 | SSH直连 | 密钥管理 |
| 13 | 删除文件 | DELETE | `/api/v1/servers/{id}/files` | 删除服务器文件 | SSH直连 | 密钥管理 |
| 14 | 获取系统服务 | GET | `/api/v1/servers/{id}/services` | 获取系统服务列表 | MQ通信 | 任务管理 |
| 15 | 管理系统服务 | POST | `/api/v1/servers/{id}/services/{name}/action` | 管理系统服务（启动/停止/重启/状态） | MQ通信 | 任务管理 |

**实现方式说明：**
- **SSH直连**：仅支持SSH直连方式，用于文件管理和终端访问
- **MQ通信**：通过任务管理Feature下发任务，Agent接收并反馈结果给任务管理
- **SSH直连+MQ通信**：SSH连接由平台直接检查，Agent和Docker状态通过MQ询问
- **-**：不涉及服务器通信，仅平台内部处理

**依赖说明：**
- **用户管理**：权限验证、所有者信息查询
- **项目管理**：资源组信息查询和验证
- **应用管理**：查询服务器上运行的应用、检查应用依赖
- **任务管理**：通过MQ下发任务并获取执行结果
- **密钥管理**：SSH认证凭据的存储、检索和安全管理
- **审计日志**：记录删除操作等重要变更

- **方法/路径**：`POST /api/v1/servers`
- **请求参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| name | string | 是 | 服务器名称 |
| hostname | string | 是 | 主机名 |
| host | string | 是 | 主机地址（IP或域名） |
| internal_ip | string | 否 | 内网IP地址 |

| ssh_key | string | 否 | SSH私钥内容（临时存储，用于后续环境检查） |
| os_type | string | 否 | 操作系统类型（可在环境检查时自动获取） |
| resource_group_id | integer | 否 | 资源组ID |
| owner_id | integer | 是 | 所有者ID |
| description | string | 否 | 服务器描述 |

#### 6.3.7 服务器操作
- **描述**：执行单个或批量服务器操作，支持系统操作和自定义命令
- **方法/路径**：`POST /api/v1/servers/actions`
- **请求参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| server_ids | array | 是 | 服务器ID列表（单个或多个） |
| action_type | string | 是 | 操作类型：system_action, custom_command |
| action | string | 是 | 具体操作内容 |
| parameters | object | 否 | 操作参数 |
| credential_id | string | 否 | 密钥管理中的凭据ID（SSH备用时使用） |
| execution_mode | string | 否 | 执行模式：sequential(顺序), parallel(并行)，默认parallel |
| parallel_limit | integer | 否 | 并行执行数量限制，默认10 |
| timeout | integer | 否 | 单个服务器操作超时时间（秒），默认300 |

**操作类型说明：**

1. **system_action**: 系统操作
   - `reboot`: 重启服务器
   - `shutdown`: 关闭服务器

2. **custom_command**: 自定义命令
   - 用户输入的shell命令

- **请求示例（系统操作）**：
```json
{
  "server_ids": [1, 2, 3],
  "action_type": "system_action",
  "action": "reboot",
  "parameters": {
    "delay": 300,
    "force": false
  },
  "execution_mode": "sequential",
  "timeout": 600
}
```

- **请求示例（自定义命令）**：
```json
{
  "server_ids": [1, 2, 3],
  "action_type": "custom_command",
  "action": "df -h && free -m && ps aux | head -10",
  "parameters": {
    "working_directory": "/home/user",
    "environment": {
      "PATH": "/usr/local/bin:/usr/bin:/bin"
    }
  },
  "execution_mode": "parallel",
  "parallel_limit": 5,
  "timeout": 60
}
```

## 9. 实现要点与关键数据流

### 9.1 服务器状态检查技术架构

**新的通信架构设计：**

```
Web UI Request
    ↓
API Service (服务器管理)
    ↓ ┌──── SSH直连检查 ────┐
    ↓ │                    │
    ↓ └──── MQ任务下发 ────┤
    ↓                      ↓
Task Management Feature    SSH连接检查
    ↓                      ↓
Redis MQ Queue            直接返回结果
    ↓                      ↓
Agent Pull模式             API响应合并
    ↓                      ↑
Target Server             │
    ↓                      │
Agent Status Report ──────┘
```

**通信方式说明：**

1. **SSH连接检查**：
   - 由服务器管理Feature直接发起SSH连接测试
   - 不依赖Agent，直接返回连接状态
   - 仅用于文件管理和在线终端功能验证

2. **Agent/Docker状态检查**：
   - 通过任务管理Feature下发MQ任务
   - Agent采用Pull模式主动获取任务并执行
   - 执行结果通过MQ反馈给任务管理Feature
   - 服务器管理Feature查询任务管理获取结果

3. **状态数据流向**：
   - Agent定期更新状态到Redis缓存
   - SSH状态由状态检查API直接验证并缓存
   - Docker状态通过Agent收集并缓存到Redis
   - 服务器管理API从Redis读取缓存状态，不进行实时检查

### 9.2 批量操作技术实现架构

**批量操作执行架构（基于MQ通信）：**

```
HTTP API Request
    ↓
Server Management API
    ↓
Task Management Feature 
    ↓
Redis MQ Queue (任务队列)
    ↓
Agent Pull模式获取任务
    ↓
Target Server执行操作
    ↓
结果反馈到MQ
    ↓
Task Management更新状态
    ↓
Server Management查询结果
```

**核心组件说明：**

1. **任务管理Feature**：
   - 接收服务器管理的批量操作请求
   - 将任务分解并发布到Redis MQ队列
   - 管理任务状态和执行进度
   - 提供任务结果查询接口

2. **Redis MQ队列**：
   - Key: `server_task:{server_id}:{task_id}`
   - 支持任务优先级和延时执行
   - Agent通过Pull模式获取任务

3. **Agent Pull模式执行**：
   - Agent定期轮询任务队列（30秒间隔）
   - 获取到任务后在本地执行
   - 执行结果反馈到指定的MQ队列

4. **任务执行策略**：
   - 所有操作均通过MQ下发给Agent执行
   - 不再使用SSH直连方式执行系统操作
   - 统一的错误处理和重试机制

**执行流程说明**：
1. 服务器管理接收批量操作请求
2. 调用任务管理Feature创建批量任务
3. 保存批次基本信息到本地数据库（轻量级记录）
4. 返回批次ID，任务执行由任务管理Feature负责
5. 查询状态时从任务管理Feature获取详细执行状态

### 9.3 批量查询技术实现架构

**查询优化策略：**

```
HTTP Query Request
    ↓
Controller Layer (分页参数验证)
    ↓
Service Layer (查询逻辑)
    ↓
Cache Layer (Redis) ←→ Database Layer (MySQL)
    ↓                        ↓
Result Aggregation    SQL Query Optimization
    ↓                        ↓
Response Formatting ← Data Combination
```

**核心优化技术：**

1. **分页查询优化**：
   ```sql
   -- 使用索引优化的分页查询
   SELECT s.*, sa.status as agent_status, sa.version as agent_version
   FROM servers s 
   LEFT JOIN server_agents sa ON s.id = sa.server_id
   WHERE s.owner_id = ? AND s.status IN (?)
   ORDER BY s.updated_at DESC
   LIMIT ? OFFSET ?
   ```

2. **缓存策略**：
   - **L1 缓存**：内存缓存（Redis），存储热点数据
   - **L2 缓存**：数据库查询结果缓存，TTL 5分钟
   - **Cache Key**: `servers:list:{user_id}:{hash(params)}:{page}`

3. **数据聚合**：
   ```go
   // 批量获取实时状态
   func GetServersWithRealTimeStatus(serverIDs []uint) ([]*ServerInfo, error) {
       // 1. 批量查询基础信息 (MySQL)
       servers, err := repo.GetServersByIDs(serverIDs)
       if err != nil {
           return nil, err
       }
       
       // 2. 批量获取实时状态 (Redis)
       statusMap, err := redis.MGetServerStatus(serverIDs)
       if err != nil {
           log.Warn("Failed to get real-time status from Redis")
       }
       
       // 3. 数据合并
       for i, server := range servers {
           if status, exists := statusMap[server.ID]; exists {
               servers[i].RealTimeStatus = status
           }
       }
       
       return servers, nil
   }
   ```

### 9.4 服务器状态管理策略

**服务器状态分类：**

### 9.6 错误处理和重试机制

**错误处理指导原则：**

错误处理采用分层设计原则：优先使用`pkg/errors`公共模块中的标准错误码和处理机制。当遇到公共模块无法覆盖的服务器管理特定场景时，在相应错误码范围内自定义新的错误码，并保持与公共模块相同的结构化和国际化支持模式。

**分层架构：**
- Application Layer → Business Logic Errors (5000-5999)
- Service Layer → Validation & Permission Errors (2000-3999)
- Communication Layer → Network & Protocol Errors (6000-6999)
- Infrastructure Layer → System & Resource Errors (4000-4999)

**服务器管理扩展错误码（业务逻辑范围5000-5999）：**
- 5020: SSH连接失败 (`server.ssh_connection_failed`)
- 5021: Agent无响应 (`server.agent_not_responding`)
- 5022: Docker服务异常 (`server.docker_service_down`)
- 5023: SSH凭据不存在 (`server.credential_not_found`)
- 5024: 批量操作部分失败 (`server.batch_operation_partial`)

**重试策略：**
- 网络/资源错误：可重试（最多3次，指数退避）
- 权限/业务错误：不重试，立即返回
- 批量操作：单个任务失败不影响其他任务执行
```

## 14. 附录

### 14.1 术语表
- **Agent**：部署在服务器上的客户端程序
- **Pull模式**：Agent主动拉取任务的通信模式
- **SSH可用性**：平台能否直接SSH连接服务器的状态
- **Host**：主机地址，可以是IP地址或域名
- **server_status**：服务器实际运行状态
- **status**：平台管理状态
- **自定义命令**：用户输入的shell命令
- **系统操作**：平台预定义的安全操作（重启、关机等）

### 14.2 状态字典

#### 服务器运行状态（server_status）
- `running`：服务器正常运行
- `stopped`：服务器已停止
- `restarting`：服务器重启中
- `unknown`：状态未知

#### 平台管理状态（status）
- `UNKNOWN`：未知状态，新创建的服务器
- `CONNECTING`：连接中，正在建立Agent连接
- `RUNNING`：运行中，Agent正常通信
- `STOPPED`：已停止，服务器关闭或Agent停止
- `ERROR`：错误状态，连接或通信异常

#### 批量操作类型
- `custom_command`：自定义命令
- `system_action`：系统操作

### 14.3 批量操作设计说明

**关于批量操作的设计原则：**

1. **错误处理策略**：
   - 遵循公共错误处理规范，返回标准格式和错误码
   - 部分服务器操作失败不影响整个批量操作继续执行
   - 每个任务独立处理，具有独立状态和错误信息

2. **批量API的必要性**：
   批量API设计是必要的，原因如下：
   - **统一事务管理**：将多个操作作为一个批量任务统一管理和跟踪
   - **执行策略控制**：支持顺序执行和并行执行模式
   - **资源限制控制**：可以限制并发数，避免系统过载
   - **状态统一查询**：通过batch_id统一查询所有任务的执行状态
   - **操作审计**：批量操作作为一个整体记录审计日志

3. **接口成功/失败判断**：
   - **接口层面**：只要请求格式正确且成功提交，就返回200（操作已提交）
   - **业务层面**：通过batch_id查询详细状态，获取每个任务的执行结果
   - **整体成功**：所有任务都成功才算批量操作成功
   - **部分失败**：部分任务失败时，批量操作状态为completed，但需查看具体任务状态
